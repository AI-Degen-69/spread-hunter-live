# Improvement Candidate — Cancel stale orders before submitting, and isolate the two calls

**Backlog item:** "Trader Loop: State machine resilience" (`SHARED_TASK_NOTES.md`)
**Category:** state machine resilience / failure isolation
**Status:** proposed, not implemented

## The defect

`_visit_one` performs the two venue-mutating steps of a market visit inside one
`try`, submit first (`core_brain/trader_loop.py:343-359`):

```python
submitted = cancelled = 0
try:
    if to_submit:
        submitted = seam.submit_fn(seam.client, seam.registry, market, to_submit, cfg)
    if to_cancel:
        cancelled = seam.cancel_fn(seam.client, seam.registry, to_cancel)
except Exception as e:
    ...
    return LiveFleetResult(status="ERROR", ...)
```

**Any exception out of `submit_fn` skips the cancels entirely.** The orders in
`to_cancel` are, by `plan_orders`' definition, orders resting at a price we no longer
want (`trader_loop.py:70-78`). They stay on the venue, at the stale price, for the whole
cycle — and for every following cycle in which the submit keeps failing.

This is not a rare path. `_submit_intents` raises **on purpose** in four places, three of
which are the safety caps themselves:

| Raise site | Trigger |
| --- | --- |
| `trader_loop.py:456-459` | a leg's notional exceeds `MAX_ORDER_USD` ($25) |
| `trader_loop.py:460-463` | `open_notional(client)` returned `None` — venue `get_open_orders` unreachable |
| `trader_loop.py:464-467` | fleet resting notional + this batch exceeds `MAX_TOTAL_USD` ($100) |
| `trader_loop.py:569-571` | a split couple was rolled back — raised after cancelling the survivor |

Plus anything the SDK throws on `create_order` / `post_orders`.

The caps are enforced by raising, and raising is exactly what disables the step that
would relieve them.

## Why it matters

Three consequences, in descending order of cost.

1. **The `MAX_TOTAL_USD` check can deadlock the fleet.** `open_notional` sums resting
   orders on the venue (`venue.py:126-138`). Once resting notional approaches $100,
   every market's submit raises, so no market cancels, so resting notional never falls.
   The only input that could reduce it is the step the exception skipped. The loop keeps
   rotating, reconcile keeps running, the dashboard keeps reading healthy, and the fleet
   is frozen holding a full book of quotes at prices it has already decided are wrong.
   Nothing in the automatic path breaks the cycle — `reconcile_orders` reconciles state
   and does not cancel, `scripts/global_stop_loss.py` contains no cancel at all, and
   `single_buy_saver` only cancels around a pair that already has fills. It takes an
   operator running `cancel-market` or `cancel-all`.

2. **Stale resting bids are the ones that get picked off.** A quote we wanted to cancel
   is a quote whose price the last `decide_quotes` rejected. Leaving it resting is
   leaving the most adversely-selected order in the book alive while its partner leg was
   never submitted. That is the shape of a **single buy** — one leg filled, one not — which
   `AGENTS.md` names as one of the two failure modes the whole system exists to prevent.

3. **A venue read blip suppresses cancels fleet-wide for that cycle.** `open_notional`
   returns `None` on any `get_open_orders` failure, which becomes a raise at
   `trader_loop.py:460-463`, which skips the cancel for that market. One flaky venue read
   and no market in the rotation retires a single stale quote.

Separately, submit-before-cancel is the wrong order even when nothing fails: between the
two calls both the old and the new order rest on the same token, doubling exposure on
that leg for the width of a venue round trip.

## Proposed change

Split the block into two independent steps and put cancel first.

1. **Cancel, then submit.** Retiring the orders we no longer want before posting the
   replacements frees venue headroom against `MAX_TOTAL_USD` before the check runs, and
   removes the double-resting window. `plan_orders` only ever puts *unwanted* orders in
   `to_cancel`, so cancel-first never drops a quote we intended to keep.
2. **A submit failure no longer costs the cancel.** The cancels have already happened and
   `cancelled` is reported on the `ERROR` result, so the operator sees what was retired
   even on a failed visit.
3. **A cancel failure refuses the submit.** If we could not retire the old orders, adding
   new ones on top is strictly more exposure than the loop asked for. Return `ERROR` with
   `submitted=0`. Flat is the safe direction; a market that stops quoting is an
   opportunity cost, a market that double-rests is a position.

Everything else in `_visit_one` is untouched, including both `emit_fn` telemetry calls
and the `DRY_RUN` / `DECLINED` early return.

## Safety

- `MAX_ORDER_USD = 25.0` and `MAX_TOTAL_USD = 100.0` are read and enforced inside
  `_submit_intents` (`trader_loop.py:454-467`) and are **not touched**. The change alters
  only *when* the cancel runs relative to the submit; every cap check still runs against
  the venue immediately before each batch, and `open_notional` is still consulted fresh.
  The caps become more effective, not less: cancels now reduce the resting notional the
  `MAX_TOTAL_USD` check reads.
- No change to `decide_quotes`, `plan_orders`, `_market_cfg`, sizing, or the pair-cost
  path. The set of orders cancelled and the set submitted are byte-identical to today;
  only their order and their failure coupling change.
- No new venue call is introduced. Cancel-first sends the same `cancel_order` calls
  `_cancel_orders` already sends (`trader_loop.py:591-611`), which swallow per-order
  failures and return a count.
- `data/orders.db` writes are unchanged: `_cancel_orders` marks the matching rows
  `cancelled`, `_submit_intents` writes its row before the venue call. Row-first-then-send
  still holds.
- Dry-run (`--no-live`) returns before this block and is unaffected.
- `core_brain/shadow_run.py` wires recorder `submit_fn`/`cancel_fn` that never raise, so
  the rehearsal path is behaviourally identical.

## Tests to add (each fails without the change)

1. `test_cancel_runs_before_submit` — a seam whose fakes append to one shared call log;
   assert the log reads `["cancel", "submit"]`.
2. `test_submit_failure_still_cancels_stale_orders` — `submit_fn` raises; assert
   `cancel_fn` was called with the stale order and the result carries `cancelled == 1`
   alongside `status == "ERROR"`. This is the regression that currently loses money.
3. `test_cancel_failure_refuses_to_submit` — `cancel_fn` raises; assert `submit_fn` was
   never called and the result is `ERROR` with `submitted == 0`.
4. `test_cap_breach_does_not_strand_stale_orders` — `submit_fn` raises the real
   `MAX_TOTAL_USD` `RuntimeError` text across two consecutive cycles; assert the stale
   order is cancelled on cycle 1 rather than re-offered on cycle 2. This is the deadlock,
   written down.

The existing `test_submit_error_does_not_stop_the_rotation` (`tests/test_trader_loop.py:220`)
still passes unchanged — it asserts `ERROR` status and that reconcile still ran, both of
which hold.

```powershell
python -m pytest -q tests/test_trader_loop.py tests/test_trader_loop_state.py tests/test_shadow_run.py
python -m pytest -q
python -m core_brain.shadow_run --minutes 2
```

`shadow_run` is the end-to-end check: no signer loaded, spends nothing, and drives the
same `_visit_one` path, confirming the reorder is invisible to the rehearsal.

## Rejected alternatives

- **Wrap the cancel in `finally`.** Keeps submit-first, so the double-resting window and
  the ordering problem survive; and a `finally` that runs after a partial-post rollback
  would cancel into a state the rollback just changed.
- **Cancel only when the submit fails.** Conditional venue mutation is harder to reason
  about than an unconditional order, and it leaves the `MAX_TOTAL_USD` headroom problem
  in place for the successful path.
- **Teach `decide_quotes` about `MAX_ORDER_USD`.** Would stop one raise class at the
  source, but it edits the sizing path — operator sign-off territory under `AGENTS.md`
  rule 4 — and does nothing for the other three raise sites. See follow-up.

## Follow-up (out of scope)

`core_brain/risk.py` sizes in dollars via `max_naked_usd` and `couple_allocation_usd` but
never reads `MAX_ORDER_USD` or `MAX_TOTAL_USD` — the venue caps are enforced only by
`_submit_intents` raising after the intents are already built. Feeding the caps into the
sizer so the decision layer produces submittable sizes, instead of the execution layer
rejecting them, is a separate candidate and touches order sizing.
